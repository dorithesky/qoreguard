QoreX · an owner signature the treasury can check

QoreGuard's README used to say "in production the owner would sign inside QoreX". This page is that step, with the eye on what the wallet actually supports today: it detects QoreX with @qorechain/qorex-types, reads the account, asks the wallet for a signature and reports the wallet's own answer — and it verifies every signature it shows against the ML-DSA-87 key registered on chain, the same key the treasury contract consults through pqcVerify.

What is actually being proved — and what is not

  

    
    
      
  1. The signature is hybrid: secp256k1 (the classical layer a quantum computer breaks) and
        ML-DSA-87 (FIPS 204). A classical-only signature is refused.
    2. 
      
  2. The ML-DSA-87 public key is not taken from the page — it is read from
        pqcKeyStatus, the precompile the treasury contract calls, so the page cannot
        substitute a key it controls.
    3. 
      
  3. The bytes are bound: one changed byte, another chain id, another signer — each is a refusal you
        can watch.
    4. 
      
  4. The treasury's own admin actions use the same primitive with a longer message
        (adminMessage), so a signature made here cannot be re-used as a payout
        approval: the domain, action and nonce differ.
    5. 
      
  5. Not proved here: that QoreX signs this text today. Its current build answers
        signArbitrary with "not yet supported" before any prompt — the button above
        reports that answer verbatim, and @qorechain/qorex-types types the call as
        Promise<never> for that reason. What does work in the wallet
        today is getKey and signAndBroadcast, which is why
        the treasury's own flow keeps the wallet out of the signing path and uses PQ-signed calls it can verify
        itself.
